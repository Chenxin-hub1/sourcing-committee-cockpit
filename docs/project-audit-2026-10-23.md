## 2026-10-26 复核

提交前逐行审查了上述改动，并把 36 份历史 Excel 用改动前后两版各解析一遍、逐字段对比。发现一处回归并已修复：

- **金额区间被当成负数**：历史文件里有 `1,76 -2,17 M€`（KW12、KW28 同一案例）这种区间写法，负号修复把 `-2,17` 读成负数，Peak Year Spend 从 2,170,000 变成 0 并多一条警告。现在紧跟在数字后面的连字符按区间处理，带单位时取紧挨单位的那个数（与改动前相同）；没有单位的 `5-6` 仍读不出，不会并成 56。
- **Currency 列的写法**：顺手让 Currency 列除 `EUR / USD / CNY` 外也认 `RMB`、`€`、`Euro`、`$`、`¥` 等写法；认不出的币种仍给警告并跳过。

修复后 36 份历史文件的解析结果与改动前完全一致。验证：611 项 Python 测试（新增 17 项：区间写法 4 例、无单位区间 2 例、币种写法 10 例、未知币种 1 例）、52 项 Chromium 功能回归、17 项滚动回归、Ruff 全部通过。

## 后续建议与现有边界

- **身份与公开数据范围**：普通用户和 Manager 凭邮箱免密登录、无需登录即可读取案例，是现有明确业务决策。公开快照还包含登记邮箱和待办收件人，Phase-31 已记录该问题；若要收紧，应先定好登录验证与各角色可见字段，再一起调整前后端，避免只隐藏页面而接口仍可读取。
- **多人编辑冲突**：同一案例仍以最后一次保存为准。使用人数增加后，建议增加记录版本号与冲突提示，防止两个编辑者互相覆盖。
- **规模与维护性**：当前完整快照、进程内写锁、单 worker 和 SQLite 适合现有小团队。数据增长后应先测量响应体大小与响应时间，再考虑按页查询和增量接口；接近 5,000 行的前端单文件可按业务功能逐步拆分，保持现有浏览器回归。
- **Excel 粘贴歧义**：`277,000` 等既可能是千分位又可能是小数的文本仍要求用户确认，这是 Phase-30 明确保留的行为；下一步需先取得实际 Excel 剪贴板 HTML 格式，再处理原始数值。
